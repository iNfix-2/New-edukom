# Edukom websites

Two independent Django applications, each with its own database, settings and process:

- `HR/`: Edukom gateway, HR consulting website, contact email and staff-managed blog.
- `learning/`: tutoring website, parent enquiries, tutor applications, staff request directory, editorial dashboard, testimonials and newsletter address collection.

These applications do not implement course delivery, grading, attendance or payroll. Existing marketing copy describes services; it is not evidence of implemented software modules.

## Local setup

Python 3.12 and Node 22 are the verified runtime targets. Run the following from **one application directory** (`HR` or `learning`), and repeat in a separate environment for the other application:

```sh
python -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
set -a
. ./.env
set +a
export DJANGO_SECRET_KEY="$(python -c 'from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())')"
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Use different ports for the two processes (for example `runserver 8000` and `runserver 8001`). Keep a stable local secret in your ignored `.env` if you want sessions to survive restarts. HR also loads its `.env` automatically; exporting variables as shown works for both sites.

The development email backend prints messages locally. It does not contact real recipients. Configure SMTP explicitly for real delivery; do not commit credentials. `learning/test_smtp.py` is an explicit command, never an import-time test connection.

## Frontend assets

Compiled assets are committed so Python-only hosting does not require Node. To rebuild after edits:

```sh
# In HR/
npm ci --ignore-scripts
npm run build:assets
# In learning/
npm ci --ignore-scripts
npm run build:css
```

Learning uses compiled Tailwind CSS; HR serves Bootstrap, icons and animation files locally. Page styles are in `HR/static/pages/` and `learning/homepage/static/pages/`. External fonts and Learning's existing icon libraries still have CDN dependencies and use available system font fallbacks.

`learning/public/Assets/` is generated by `collectstatic`, is ignored by Git and must be recreated during deployment. Its unique images were preserved in the source static directory. This removes duplicate framework and image files from version control.

The original HR imagery was not committed. Missing portraits and client logos now use names or initials, and illustrative panels use text. Supply approved originals to replace those treatments; unrelated people or fabricated client logos have not been substituted.

## Verification

From each application directory:

```sh
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
python manage.py collectstatic --noinput
```

The regression suite covers permissions, record lookup errors, CSRF and POST deletion, atomic applications, private receipts, notification failure/retry, contact validation, HTML sanitization, management navigation, pagination and admin rendering. CI repeats setup, migration, asset build and tests for both applications.

Browser layout checks remain outstanding: this execution environment could not launch its local Chromium and the cloud browser could not access the development server. HTTP/template and static-file checks are not a substitute for visual desktop/mobile review.

## Deployment and existing databases

1. Rotate the previously committed SMTP password at the mail provider. Generate a new production Django secret for each site. Account hashes and session data were removed from `HR/db.json`, but old Git revisions still contain them; reset affected account passwords and revoke sessions on any corresponding live system. This change does not rewrite repository history or change live credentials.
2. Install the pinned requirements, including Django 5.2.19. Review the Django upgrade against a backup of the existing deployment before rollout; this change was tested with fresh databases, not the live database.
3. Set `DJANGO_DEBUG=false`, a strong `DJANGO_SECRET_KEY`, explicit comma-separated `DJANGO_ALLOWED_HOSTS`, and HTTPS `DJANGO_CSRF_TRUSTED_ORIGINS`. Configure `EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend` and the mail credentials. HR can use MySQL with `USE_SQLITE=false` and its `MYSQL_*` settings; install `mysqlclient` separately for that deployment. Learning currently uses SQLite.
4. Back up the existing database and media, inspect the migration history and compare the actual schema with the new initial migrations on a staging copy. For a **fresh** database use `python manage.py migrate`. For an existing database whose tables and schema already match, `migrate --fake-initial` may be appropriate. It only detects table existence, not full schema compatibility; do not use it blindly. Do not regenerate or delete live migration history as a shortcut.
5. Run `collectstatic --noinput` and map `/static/` to `HR/staticfiles/`, `/Assets/` to `learning/public/Assets/`, and each site's `/media/` to its media directory. Preserve uploaded media on durable storage. HR's optional S3 backends use Django's `STORAGES` setting.
6. Run `python manage.py check --deploy` with production environment variables. HTTPS redirect, secure cookies and HSTS are enabled outside debug. Domain-wide HSTS and preload are deliberately opt-in: the default report includes `security.W005` and `security.W021`. Enable these only after verifying all subdomains and deciding to submit the domain for preload. Configure HTTPS termination accurately; do not set proxy trust headers for untrusted inbound requests.
7. Smoke-test forms, staff access, the private receipts and both mobile/desktop layouts before switching traffic. Startup failures return a generic 503 and record the traceback only in server logs.

The cleaned `HR/db.json` includes blog content only. It does not supply accounts. Create accounts separately and grant staff access intentionally. Ordinary users cannot access parent or tutor records.

## Notifications

Applications save their related records atomically. Email is sent after saving, not from a GET confirmation page. Receipts are restricted to the submitting browser's session. A successful notification marker is saved only when both the applicant email and staff email are accepted by the backend. SMTP acceptance does not guarantee inbox delivery.

To retry applications without a successful marker, run explicitly from `learning/`:

```sh
python manage.py retry_notifications
```

Do not run retries concurrently. If the applicant email succeeds but the staff email fails, a retry can resend the applicant email. This is a synchronous delivery flow, not a queued exactly-once delivery system. Contact enquiries remain saved in Learning's admin when notification delivery fails.

HR's playbook CTA now leads to the contact form. It no longer presents a subscription that did not save or deliver anything. Learning's newsletter stores addresses; a campaign delivery integration is outside the current implementation.
